## Design Decisions

### 1. AI Boundary

**Decision**: SDK is the ONLY interface AI needs to understand

**Rationale**:
- Compiler core (Mapper, IR, Writers) is frozen and opaque
- AI never generates XML or BPMN directly
- All SAP-specific knowledge in Registry (hidden from AI)
- AI focuses on high-level business logic

**Benefit**: Future compiler improvements don't require retraining AI

---

### 2. Validation-First Approach

**Decision**: Detect errors before ZIP generation

**Rationale**:
- Faster feedback loop for AI
- Clear error messages enable self-correction
- Prevents invalid flows reaching compilation

**Layers**:
1. TypeScript type system (compile-time)
2. Validation Engine (pre-compilation)
3. ComponentMapper (compilation)
4. Writers (serialization)

---

### 3. Fluent API Emphasis

**Decision**: Method chaining for all SDK operations

**Rationale**:
- More readable for AI-generated code
- Matches natural language structure
- Enables pattern recognition

**Example**:
```typescript
flow.addComponent(a).addComponent(b).connect(a, b);
```

---

### 4. Explicit Anti-Patterns

**Decision**: Document what AI must NOT do

**Rationale**:
- Prevents common mistakes
- Guides AI toward correct patterns
- Reduces trial-and-error

**Categories**:
- Don't generate XML
- Don't use compiler internals
- Don't hardcode SAP metadata
- Don't create custom component types

---

### 5. Machine-Readable Metadata

**Decision**: Provide JSON schema alongside markdown docs

**Rationale**:
- Enables programmatic validation
- AI can parse constraints directly
- Supports automated testing

**Format**: JSON with JSON Schema structure

## Validation Engine Design (Recommended Next)

Based on VALIDATION_RULES.md, here's the recommended architecture:

### Class Structure

```typescript
// Main engine
class ValidationEngine {
    validate(flow: IFlow): ValidationResult
    validateComponent(component: Component): ValidationIssue[]
    validateConnections(flow: IFlow): ValidationIssue[]
    validateResources(flow: IFlow): ValidationIssue[]
}

// Result
interface ValidationResult {
    valid: boolean;
    errors: ValidationIssue[];
    warnings: ValidationIssue[];
    infos: ValidationIssue[];
}

// Issue
interface ValidationIssue {
    ruleId: string;
    level: "ERROR" | "WARNING" | "INFO";
    message: string;
    details: string[];
    fix: string;
    example?: string;
    location?: {
        component?: string;
        property?: string;
    };
}

// Rule interface
interface ValidationRule {
    id: string;
    level: "ERROR" | "WARNING" | "INFO";
    check(flow: IFlow): ValidationIssue[];
}
```

### Rule Implementation Example

```typescript
class IF003_ComponentUniqueness implements ValidationRule {
    id = "IF-003";
    level = "ERROR";
    
    check(flow: IFlow): ValidationIssue[] {
        const issues: ValidationIssue[] = [];
        const ids = new Map<string, number>();
        
        flow.getComponents().forEach((comp, index) => {
            if (ids.has(comp.id)) {
                issues.push({
                    ruleId: this.id,
                    level: this.level,
                    message: `Duplicate component ID '${comp.id}'`,
                    details: [
                        `Component '${comp.name}' (${comp.componentType}) at position ${ids.get(comp.id)}`,
                        `Component '${comp.name}' (${comp.componentType}) at position ${index}`
                    ],
                    fix: "Ensure each component has a unique ID",
                    example: "const comp = new Component(`CMP_${Date.now()}`, ...)"
                });
            }
            ids.set(comp.id, index);
        });
        
        return issues;
    }
}
```
